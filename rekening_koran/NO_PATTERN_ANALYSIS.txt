CASE 3: BTP 2300014763
═══════════════════════════════════════════════════════════════════

Data:
  • Total Transaksi: 136
  • Unique Customers: 40 (banyak!)
  • Customer Dominan: "DAVID TANTRIS OR F" → 97 (71.3%)
  
  Top customers:
    1. DAVID TANTRIS OR F → 97 (71.3%)
    2. N7159289 DAVID TANTRIS OR F → 1 (0.7%)
    3. N7148815 DAVID TANTRIS OR F → 1 (0.7%)
    ... dan 37 lainnya dengan invoice berbeda

❌ PROBLEM: Invoice Number Masuk ke Customer Name
───────────────────────────────────────────────────────────────────

  Alasan:
  • Sebenarnya customer sama: "DAVID TANTRIS OR F"
  • Tapi ada variasi dengan invoice number di depan
  • Program detect sebagai 40 customer berbeda!
  • Customer dominan cuma 71.3% (< threshold 80%)
  • Tidak masuk ke master data

  Analisis Detail:
  • 97 transaksi pakai format: "... DAVID TANTRIS OR F"
  • 39 transaksi pakai format: "... N7xxxxx DAVID TANTRIS OR F"
  • Variasi invoice number: N7159289, N7148815, K002000026399, dll
  • Setiap invoice number detect sebagai customer berbeda

  Solusi:
  → Data cleansing: remove invoice pattern (N7xxxxx, K002xxxxxx)
  → Better pattern extraction: ignore invoice sebelum customer name
  → Standardize format deskripsi
  → Manual mapping sementara

📋 KESIMPULAN: PENYEBAB NO PATTERN (Berdasarkan Investigation)
═══════════════════════════════════════════════════════════════════

1. 🏆 NAMA TERPOTONG (Most Common)
   ───────────────────────────────────────────────────────────────
   • Deskripsi CSV dipotong karena limit karakter
   • Nama full di master tapi di CSV cuma sebagian
   • Contoh: "KOKUMINDO BERKAT M" vs "KOKUMINDO BERKAT MANDIRI"
   
   Impact: ~30-40% dari NO PATTERN cases
   
   Fix:
   ✓ Cek nama lengkap di raw data
   ✓ Update master dengan nama terpotong juga (alias)
   ✓ Atau extend CSV field length


2. 💥 INVOICE/NOMOR MASUK KE PATTERN (Common)
   ───────────────────────────────────────────────────────────────
   • Nomor invoice/nota ikut ke-detect sebagai customer name
   • Setiap transaksi detected berbeda karena nomor beda
   • Contoh: "N7159289 DAVID" vs "N7148815 DAVID"
   
   Impact: ~20-30% dari NO PATTERN cases
   
   Fix:
   ✓ Better extraction: ignore pattern N[0-9]+ atau K00[0-9]+
   ✓ Data cleansing: standardize format
   ✓ Regex untuk strip invoice number


3. 🎲 MULTIPLE CUSTOMERS REAL (Normal)
   ───────────────────────────────────────────────────────────────
   • BTP memang dipakai untuk banyak customer kecil-kecil
   • Tidak ada yang dominan (semua < 80%)
   • Business case yang valid
   
   Impact: ~15-20% dari NO PATTERN cases
   
   Fix:
   ✓ Ini normal, tetap pakai manual entry
   ✓ Atau buat multiple entries untuk top customers


4. 📉 TRANSAKSI TERLALU SEDIKIT (Normal)
   ───────────────────────────────────────────────────────────────
   • BTP punya < 2 transaksi
   • Tidak reliable untuk pattern matching
   
   Impact: ~10-15% dari NO PATTERN cases
   
   Fix:
   ✓ Ini normal, tunggu accumulate transaksi
   ✓ Will auto-masuk di refresh berikutnya


5. 📝 TIDAK ADA CUSTOMER NAME (Normal)
   ───────────────────────────────────────────────────────────────
   • Format lama atau deskripsi tidak lengkap
   • Hanya ada metadata transaksi
   
   Impact: ~5-10% dari NO PATTERN cases
   
   Fix:
   ✓ Data enrichment: tambah customer name
   ✓ Atau tetap manual entry
